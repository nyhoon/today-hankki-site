# 오늘한끼 운영 대시보드 설계안

상태: 구현 완료 · 로컬 자동 검사 통과 · 운영 DB 미반영
작성일: 2026-10-02

## 목표와 합의된 제약

- 운영자가 Supabase 콘솔을 열지 않고도 게시물, 계정, 키친, 푸시, 식재료, 레시피, 정책 운영을 한 곳에서 처리한다.
- 데스크톱은 사이드바, 좁은 화면은 접히는 메뉴와 한 열 화면을 사용한다.
- 홈 차트 기간은 일별·주별·월별·연별로 바꾼다.
- 모든 모듈의 생성·조회·수정·삭제 범위를 정의한다. 항목 특성상 영구 삭제가 맞지 않으면 숨김·보관·철회 같은 되돌릴 수 있는 작업을 기본으로 한다.
- 브라우저에는 Supabase publishable key만 둔다. service role key와 인증 관리 비밀값은 브라우저에 전달하지 않는다.
- 모든 운영 변경은 서버 측 권한 확인, 입력 검증, 운영 감사 기록을 거친다. 브라우저 UI의 메뉴 숨김은 권한 검사가 아니다.
- 제철 정보는 출처와 확인 시점을 함께 보여준다. 제철이라는 표시를 신선도·안전 보증으로 쓰지 않는다.

## 화면 구조

### 1. 홈

대기 검토, 열린 신고, 공개 사용자 레시피, 가입자 수를 요약하고, 기간 선택에 따라 신규 계정·공개 레시피·신고·푸시 발송 추이를 그린다. 차트는 지표를 선택할 수 있고, 모바일에서는 한 차트씩 세로로 쌓는다. 현재 저장되지 않는 지표는 숫자 0으로 위장하지 않고 “수집되지 않는 항목”으로 표시한다.

### 2. 커뮤니티

탭 또는 필터로 레시피·후기·신고를 나눈다. 대기 레시피는 전체 내용과 작성자를 확인한 뒤 승인 또는 사유를 기록해 반려한다. 공개 레시피와 후기는 숨김·복구를 지원한다. 신고는 처리·기각 상태로 보존한다. 좋아요·팔로우는 조회와 이상 활동 확인을 지원하되 운영자가 사용자 대신 관계를 만들어내지 않는다.

### 3. 사용자

계정 검색과 상세 보기를 제공하고, 프로필·가입 시각·로그인 제공자·소속 키친·커뮤니티 활동·제재 이력을 보여준다. 이용 제한과 해제를 지원한다. 계정 영구 삭제는 일반 편집에서 분리하고 사유·재확인·감사 기록을 요구한다. 브라우저에서 Auth Admin API나 service role을 직접 호출하지 않는다.

### 4. 키친·초대

키친, 구성원 역할, 초대 상태를 조회하고 초대를 철회한다. 역할 변경과 구성원 제거는 서버에서 키친 소유권·공유 데이터 영향을 검증한다. 키친 보관·삭제는 구성원과 데이터 영향을 먼저 요약하고 소유권 규칙을 적용한다.

### 5. 식재료·레시피

표준 식재료 이름·별칭·아이콘, 식약처 재료명과의 연결, 상품 바코드 연결, 공식 레시피와 재료 매핑을 관리한다. 새 표준 항목은 추가할 수 있고, 사용 중인 항목은 영구 삭제 대신 보관 처리한다. 실제 참조가 없는 항목만 사유를 기록한 뒤 영구 삭제할 수 있다. 추후 월별 제철 항목도 같은 화면에서 출처·월·표준 식재료 연결을 관리하도록 확장한다.

### 6. 푸시 운영

푸시 설정, 기기 수, 발송·실패 기록을 조회한다. 예약 일정과 문구를 관리하고 운영자 본인 기기로 테스트 발송한다. 단체 발송은 대상·내용·예약 시각을 미리 확인하고, 중복 발송 방지 키와 발송 상한을 서버에서 검증한다. 토큰 원문은 화면에 노출하지 않는다.

### 7. 정책·운영자

약관·개인정보처리방침 초안을 만들고 편집한다. 게시된 버전은 수정하지 않고 새 버전으로 발행한다. 운영자 추가·철회는 기존 운영 권한을 서버에서 재검증하고 감사 로그에 남긴다.

### 8. 감사 로그·서비스 상태

감사 로그는 검색·필터·상세 보기는 허용하되 수정·삭제하지 않는다. DB·Storage·푸시·로그인 상태는 읽기 전용으로 보여준다. 실제 상태 점검이 구성되지 않은 항목은 임의로 정상이라고 표시하지 않는다.

## 권한과 서버 변경

구현 결과와 검증 상태는 아래 `2026-10-02 구현·검증`을 따른다. 모든 변경은 다음 서버 경계를 유지해야 한다.

1. 모든 쓰기 RPC 또는 Edge Function에서 로그인 세션과 운영자 권한을 다시 확인한다.
2. RLS 및 함수 권한은 최소 권한으로 설정하고, `SECURITY DEFINER` 함수는 고정된 `search_path`와 명시적 입력 검증을 사용한다.
3. 관리 대상별 작업을 원자적으로 처리하고, actor·작업·대상·사유·변경 요약·시각을 감사 로그에 저장한다.
4. 통계는 실제 생성·발행·발송 시각을 기준으로 집계한다. 일별·주별·월별·연별 구간 정의와 서울 시간대를 서버에서 통일한다.
5. 운영자 계정, 계정 제한, 키친 삭제, 푸시 일괄 발송 같은 고위험 작업은 UI 확인 외에도 서버에서 별도 권한과 사유를 요구한다.

## 화면 동작과 접근성

- 데스크톱 사이드바는 현재 선택 위치와 대기 건수를 표시한다. 모바일에서는 상단 메뉴 버튼으로 접고, 화면 선택 시 닫는다.
- 표는 모바일에서 카드 행으로 바뀌며, 검색·상태 필터·정렬을 유지한다.
- 저장·승인·숨김 작업 중에는 중복 입력을 막고 결과를 화면에 알린다. 실패하면 입력 내용을 보존한다.
- 영구 삭제 전에는 대상·영향 범위·입력한 사유를 재확인한다.
- 키보드 이동, 명확한 포커스, 대비, 44px 이상의 조작 영역, 스크린 리더 이름을 지원한다.
- 차트는 색상만으로 구분하지 않고 범례와 표 형태의 접근 가능한 값도 제공한다.

## 구현 순서

1. 대시보드 응답형 셸·사이드바·모바일 메뉴·공통 검색/필터/확인 UI
2. 홈 지표와 기간별 차트, 실제 데이터 범위 검증
3. 커뮤니티 운영 CRUD와 감사 로그
4. 사용자 및 키친 운영 RPC/Edge Function과 화면
5. 식재료·공식 레시피 매핑 관리
6. 푸시 일정·테스트 발송·이력 관리
7. 정책·운영자 권한 관리, 읽기 전용 상태·감사 로그 화면
8. 보안·모바일·접근성 테스트, 배포 미리보기 검토

각 단계는 로컬/개발 Supabase에서 먼저 확인한다. 운영 데이터에 쓰는 RPC와 마이그레이션은 미리보기와 회귀 점검 후 별도 운영 반영 단계에서 승인받는다.

## 다음 단계: 무료 추천과 제철 데이터

이 단계에서는 유료 모델 호출을 늘리지 않는다. 앱에는 이미 재고와 레시피의 재료 연결·보유율·기한 임박도를 기준으로 계산하는 `rankRecipes`가 있고, 별도의 `recommend-recipes` 서버 함수는 OpenAI Responses API를 호출한다. 다음 단계에서는 기본 추천을 규칙 기반으로 유지·개선하고, 추천 이유는 매칭 결과에 근거한 템플릿으로 표시하는 방안을 먼저 평가한다. 이 방식은 모델 API 호출료를 발생시키지 않지만 Supabase DB·전송량은 기존 요금제 한도의 적용을 받는다. 제철 정보는 앱 내 공식 식재료 연결에 월별 제철 ID를 더해 추천 점수에 작은 가산점으로 사용할 수 있다.

웹사이트 작업본에는 이미 12개월 제철 재료 찾아보기와 출처 링크를 둔 정적 페이지가 있다. 이를 다시 만들지 않고, 대시보드·앱과 연결할 때 데이터의 출처·갱신일·표준 재료 매칭을 이어서 검토한다. 제철은 맛과 구매 선택을 돕는 참고 정보로만 취급하며 재료 안전이나 신선도 판정에 사용하지 않는다.

## 미해결 조건

- Figma 계정의 현재 좌석은 `View`다. 편집 가능한 좌석이 확인되면 기존 승인 범위의 화면 시안을 Figma에 저장한다. 현재는 이 명세가 검토 가능한 설계 산출물이다.
- 시스템 상태, 방문/행동 분석의 일부는 현재 데이터 적재 기반이 확인되지 않았다. 실제 수집원을 정하기 전에는 그래프를 만들지 않고 준비 상태를 표시한다.
- 운영자 계정 관리·사용자 제한·키친 운영·푸시 예약에는 새 서버 권한과 RPC/Edge Function이 필요하다. 기존 승인·반려 RPC를 브라우저에서 임의로 확장하지 않는다.

## 2026-10-02 구현·검증

홈과 7개 운영 모듈을 반응형 사이드바 대시보드에 연결했다. 검색·페이지 조회, 차트 기간 선택, 커뮤니티 검토·신고, 사용자 제한, 키친 보관·초대 철회, 카탈로그 관리, 푸시 템플릿·예약, 정책 버전, 운영자 권한, 감사 로그를 지원한다. 쓰기는 전용 RPC/Edge 경로에서 운영자 UID를 검증하며 브라우저에는 publishable key만 둔다. Google 운영자 추가와 최초 등록은 Auth 이메일과 `email_verified=true` Google identity 이메일이 일치해야 한다. 레시피 제출에는 현재 약관 동의 확인이 필수이고 사진은 선택이다.

검증 결과: `node --check admin-v3.js` 통과, 대시보드·제철 페이지 Node 테스트 11/11 통과, 로컬 `/admin.html` HTTP 200. 앱 저장소에서는 Flutter 분석과 테스트 86개, 푸시 로직 테스트 8개, PGlite 전체 40개 migration 적용 및 DB 스모크 검사 31개가 통과했다. 운영자 권한 pgTAP 23개와 커뮤니티 pgTAP 15개는 작성했지만 Docker 기반 로컬 Supabase가 없어 실행하지 못했다. Deno Edge 런타임 검사와 브라우저 375–1440px/키보드 시각 검수도 미완료다.

운영 Supabase에는 migration을 적용하지 않았다. `main:/`이 GitHub Pages 공개 원본이므로 사이트 저장소를 푸시하면 대시보드와 제철 페이지가 자동 발행된다. Figma 파일은 만들었지만 MCP 쓰기 한도에 막혀 화면 레이어를 저장하지 못했다. 정적 SVG 시안은 앱 저장소의 설계 문서에 보관한다. 추천·제철 데이터의 앱 추천 연동은 후속 작업이다.
